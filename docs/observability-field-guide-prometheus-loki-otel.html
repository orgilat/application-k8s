Prometheus Fundamentals

What you must understand before touching a keyboard — the model, the storage engine, the metric types, and the PromQL rules that will fail you silently if you don't know them.

Pull vs. push, and why it's an operational decision, not a taste preference

Prometheus is a pull-based monitoring system. It does not wait for applications to send it data. Instead, on a fixed interval, Prometheus reaches out over HTTP to each configured target and issues a plain GET /metrics request. The target responds with a flat text document — the Prometheus exposition format — listing every metric it currently knows about. Prometheus parses that response, timestamps every line with "now", and writes the samples to its local storage.

Contrast that with a push-based system (StatsD, Graphite's classic carbon-cache, or CloudWatch custom metrics): the application itself decides when to emit a data point and fires it at the collector, usually over UDP or a lightweight TCP protocol, with no acknowledgement that anyone received it.

This is not a stylistic difference. It changes what failures look like and what you can prove:

  • Target health becomes a first-class signal. Every scrape attempt produces a synthetic metric, up{job="...", instance="..."}, set to 1 if the scrape succeeded and 0 if it didn't (connection refused, timeout, non-200 response). With push, if an app stops sending data, you cannot distinguish "the app is fine and has nothing new to report" from "the app is dead and can no longer push." Silence is ambiguous in push; in pull, silence is itself a scrape failure you can alert on directly.
  • Configuration lives in one place. Prometheus's own config file is the single source of truth for what is being monitored and how often. You don't need to configure hundreds of application instances with "here is the collector's address" — you tell Prometheus where they are, once.
  • No thundering herd. Every pushing client deciding independently when to send data means bursts and contention at the collector. Prometheus staggers its own scrape schedule internally across targets, so load on both sides is predictable.
  • The trade-off is reachability. Pull only works if Prometheus can open a connection to the target. This is trivial inside a stable network (a VM, a Kubernetes cluster, a Docker network) and becomes a real architectural problem the moment the "target" is short-lived or unreachable — a Lambda invocation, a CI runner, an ECS task that dies seconds after starting. That exact problem is the entire subject of Part 3.
Why this matters in an interview

If asked "why does Prometheus use pull," the wrong answer is "it's simpler." The right answer is: pull makes target liveness an explicit, queryable signal (up), centralizes configuration, and avoids collector overload from uncoordinated clients — at the cost of requiring network reachability from Prometheus to every target, which is precisely why ephemeral compute needs an exporter or Pushgateway pattern instead of being scraped directly.

Core architecture: TSDB, WAL, retention, jobs, and targets

Prometheus stores everything in its own purpose-built time-series database (TSDB) — there is no external database dependency for core functionality. Internally:

  • The head block is the most recent, still-mutable chunk of data, held in memory for fast writes and queries. Every scrape appends to it.
  • The WAL (write-ahead log) is written to disk before a sample is considered durable in memory. If Prometheus crashes, it replays the WAL on startup to reconstruct the in-memory head block — this is what prevents a crash from silently losing the last few minutes of scraped data.
  • Compaction periodically flushes the head block into immutable, on-disk blocks (2-hour ranges initially, merged into larger blocks over time). This is why Prometheus disk usage grows in visible chunks rather than smoothly.
  • Retention — controlled by --storage.tsdb.retention.time (default 15 days if you never set it) and optionally --storage.tsdb.retention.size — determines when old blocks get deleted. Whichever limit is hit first wins.

Two labels are attached to every single sample Prometheus scrapes, and confusing them is a common interview stumble:

  • job — the name you gave the job_name: in scrape_configs. It identifies what kind of thing you're scraping — a logical group, e.g. automation-results-exporter, regardless of how many instances of it exist.
  • instance — the specific host:port of the individual target that was scraped, e.g. automation-exporter:9091. If you scale a job to 5 replicas, you get one job label shared across 5 distinct instance values.

A target is one scrapeable endpoint (one instance). A job is the named group of targets serving the same role, discovered via one scrape_configs entry — whether that entry lists targets statically, reads them from a file, or asks Docker/Kubernetes for the current list.

The four metric types — and the one distinction that actually gets tested

TypeBehaviorReal example
CounterMonotonically increasing. Only goes up (or resets to 0 on process restart). Never use its raw value — always wrap in rate() or increase().automation_tests_total-style running totals; http_requests_total
GaugeA value that can go up or down freely. Represents current state.automation_pass_rate, automation_consecutive_failures, memory usage
HistogramBuckets observations into configurable, cumulative le (less-than-or-equal) buckets, plus a _sum and _count. Quantiles are computed server-side, at query time, and can be aggregated across instances.automation_run_duration_seconds with buckets at 60s, 120s, 180s...
SummaryComputes configurable quantiles (p50/p90/p99) client-side, at observation time, and exposes the pre-computed result plus _sum/_count.Legacy client libraries' default latency metric

The distinction that actually matters operationally: a summary's quantiles are computed inside the process being measured, per-instance, and cannot be meaningfully averaged or re-aggregated across instances — you cannot average two p99s together and get a correct fleet-wide p99. A histogram, by contrast, exposes raw bucket counts, which can be summed across every instance in a job and then have a quantile computed once over the combined data. Because almost everything you monitor runs on more than one instance, or you at least want the option to scale later, default to histograms. Reach for a summary only when you need an exact (not bucket-estimated) per-instance quantile and are certain you will never need to aggregate across instances.

PromQL fundamentals

An instant vector is a set of time series, each with exactly one sample, at one point in time — what you get from a bare metric name like automation_pass_rate. A range vector is a set of time series where each series carries multiple samples over a time window, produced by appending a duration in square brackets: automation_pass_rate[5m]. Range vectors cannot be graphed directly — they exist to be fed into functions like rate(), increase(), or histogram_quantile()'s inner aggregation.

rate() vs. irate() vs. increase()

  • rate(x[5m]) — average per-second rate of increase over the whole 5-minute window, extrapolated to the window's edges, and it automatically handles counter resets (a restart that drops the counter back to 0). Use this for alerting and any graph you intend to reason about over minutes-to-hours — it smooths out noise.
  • irate(x[5m]) — uses only the last two data points inside the window to compute an instantaneous rate. Great for a live, fast-twitch dashboard of a volatile counter, but never use it for alerting — a single noisy scrape can trigger or silence an alert that rate() would have kept correctly smoothed.
  • increase(x[1h]) — the total increase over the window (conceptually rate() × window seconds, with the same reset-handling and extrapolation). Use this when you want an absolute count phrased in human terms: "how many failed runs in the last 24 hours," not a per-second rate.

Aggregation operators

sum(), avg(), max(), min(), count(), and topk(n, ...) collapse multiple series into fewer. by (label1, label2) keeps only the named labels and groups on them (everything else is dropped). without (label1) does the inverse — drop only the named label(s), keep everything else. Both change which labels survive on the resulting series, which is exactly the trap in the next section.

The histogram_quantile() trap — memorize this

This is the single most common silent-failure PromQL pattern, and it will not throw an error. It will simply return a wrong (or garbage-looking, or empty) number, with no warning.

histogram_quantile() requires its input range vector to be grouped only by le (plus whatever dimension you deliberately want to keep, like job). If the bucket series still carry a high-cardinality label — say, instance, because you're scraping three replicas of the same job — you get multiple overlapping, independent bucket ladders per le value instead of one clean monotonic ladder, and the quantile interpolation math falls apart silently.

Broken
histogram_quantile(
  0.95,
  rate(http_request_duration_seconds_bucket[5m])
)

If http_request_duration_seconds_bucket is scraped from three pods behind one job, this query is operating on series like:

http_request_duration_seconds_bucket{instance="10.0.0.1:8080", le="0.5"}
http_request_duration_seconds_bucket{instance="10.0.0.2:8080", le="0.5"}
http_request_duration_seconds_bucket{instance="10.0.0.3:8080", le="0.5"}

histogram_quantile() tries to reconstruct one bucket ladder per unique remaining label set, but three different instances is not what it expects for one quantile — you'll get either three separate (meaningless, per-instance) quantiles smeared together, or, worse, an interpolation across a non-monotonic mash of buckets that produces a number that looks plausible but is wrong. No error. No warning. Just a wrong p95 that you will ship into a dashboard and trust.

Fixed
histogram_quantile(
  0.95,
  sum(rate(http_request_duration_seconds_bucket[5m])) by (le)
)

The fix: aggregate away every label except le before handing the result to histogram_quantile(). sum(...) by (le) collapses the three instances' buckets into one true combined ladder, per le, across the whole job — and only then does the quantile math have a single, monotonic, correct bucket ladder to interpolate against. If you want to keep the quantile split by job (multiple jobs sharing a dashboard), add it to the by clause: by (le, job) — but never leave instance, pod, or any other per-replica label in there.

This exact pattern is already correct in this repo's own dashboard query:

histogram_quantile(0.95, rate(automation_run_duration_seconds_bucket[7d]))

That specific query happens to be safe today only because the exporter runs as a single instance — there is exactly one instance label value in play, so no aggregation is strictly required. The moment anyone scales the exporter to two replicas for availability, this query silently starts producing wrong numbers unless sum(...) by (le) is added first. Flag this as a landmine, not a bug — it's correct today, fragile tomorrow.

Building Prometheus Completely From Scratch

A real docker run, a real prometheus.yml, the exact Docker DNS mechanics that make container-name scraping work — and a full incident narrative for when it doesn't.

Running Prometheus as a standalone container

bash
docker network create observability_default

docker run -d \
  --name prometheus \
  --network observability_default \
  -p 9090:9090 \
  -v prometheus_data:/prometheus \
  -v "$(pwd)/prometheus.yml:/etc/prometheus/prometheus.yml:ro" \
  --restart unless-stopped \
  prom/prometheus:v2.52.0 \
  --config.file=/etc/prometheus/prometheus.yml \
  --storage.tsdb.retention.time=90d \
  --web.enable-lifecycle

Flag by flag, and why each one is there:

  • -d — detached mode; the container runs in the background and docker run returns immediately with the container ID. This matters for the case study below: "the command returned successfully" only ever means "the container was created and started," never "the process inside is healthy."
  • --name prometheus — without an explicit name Docker assigns a random one (affectionate_turing), which is useless for DNS-by-name resolution from other containers. Naming it deliberately is what makes http://prometheus:9090 resolvable from anywhere else on the same network.
  • --network observability_default — attaches the container to a user-defined bridge network. This single flag is the difference between name-based resolution working and failing outright — explained in full below.
  • -p 9090:9090 — publishes the container's port 9090 to the host's port 9090. This is what lets you (or Grafana, if Grafana runs outside Docker) reach it via the host's IP. If Grafana is itself a container on the same Docker network, it does not need this published port at all — it can reach prometheus:9090 directly over the internal network.
  • -v prometheus_data:/prometheus — a named Docker volume mounted at Prometheus's data directory. Named volumes are managed by Docker, survive docker rm of the container, and avoid host-filesystem permission mismatches (the Prometheus image runs as a non-root UID). Never point this at an arbitrary host path unless you've deliberately matched UID/GID permissions.
  • -v "$(pwd)/prometheus.yml:/etc/prometheus/prometheus.yml:ro" — a bind mount, read-only, of your actual config file from the host into the container. Bind-mounting config (rather than baking it into a custom image) means editing the file on the host and reloading takes effect immediately, with no rebuild.
  • --config.file=... — tells the Prometheus binary itself where its config lives inside the container. This is a Prometheus CLI flag, not a Docker flag — it must match wherever you mounted the file.
  • --storage.tsdb.retention.time=90d — overrides the default of 15 days. If you never set this flag, Prometheus deletes data older than 15 days regardless of how much disk you have.
  • --web.enable-lifecycle — turns on the POST /-/reload endpoint, letting you push a config change (curl -X POST http://localhost:9090/-/reload) without restarting the container. Without this flag, the only way to pick up a new prometheus.yml is a full restart, which briefly drops the in-memory head block state and any in-flight scrapes.

Writing prometheus.yml from scratch

infra/grafana-server/prometheus.yml
global:
  scrape_interval: 60s
  evaluation_interval: 60s

scrape_configs:
  - job_name: 'automation-results-exporter'
    static_configs:
      - targets: ['automation-exporter:9091']
    scrape_interval: 60s
  • global.scrape_interval — the default cadence applied to every job that doesn't override it. 60s here means "assume nothing changes faster than once a minute," which is correct for this workload — the exporter itself only refreshes from S3 every 60s, so scraping faster would just re-read identical numbers.
  • global.evaluation_interval — how often Prometheus re-evaluates recording rules and alerting rules (not scraping — a separate clock).
  • scrape_configs — the list of jobs. Each entry becomes one job label value.
  • job_name — the literal string that becomes the job label on every sample from this entry.
  • static_configs.targets — a list of host:port strings. Each one becomes an instance label, and — critically — the host part (automation-exporter) is resolved as a DNS name, not an IP literal, which is exactly where Docker networking enters the picture.
  • per-job scrape_interval — overrides the global default for just this job. Here it's redundant with the global value but written explicitly for clarity/future-proofing if the global default ever changes.

Docker networking in depth: why the network flag isn't optional

Docker's default bridge network (the implicit network every container joins if you don't specify one) does not run a name-resolution service. Containers on it can only reach each other by IP address — there is no DNS server listening for container names.

A user-defined bridge network (anything you create with docker network create, or that Docker Compose creates automatically per project) is different: Docker runs an embedded DNS resolver at 127.0.0.11 inside every container attached to that network, and it resolves other containers' names (and any network_alias) to their current internal IP. This is what makes http://automation-exporter:9091 work from inside the Prometheus container — "automation-exporter" is a DNS name that only resolves correctly on that specific network.

The failure mode when a container is not on the right network is one of the most common Docker gotchas in production, and it has a distinctive signature:

Symptom textWhat it means
dial tcp: lookup automation-exporter: no such hostPlain DNS failure — the name genuinely doesn't exist anywhere the resolver checked (e.g. no embedded Docker DNS at all, such as on the default bridge network).
dial tcp: lookup prometheus on 127.0.0.11:53: server misbehavingThe request did reach Docker's embedded DNS server (127.0.0.11) but it could not resolve the name — almost always because the querying container is on a different user-defined network than the container it's trying to reach, so the embedded resolver on network A has never heard of a container that only exists on network B.

Diagnosing it live:

bash
# What containers are actually attached to this network?
docker network inspect observability_default

# What network(s) is this specific container actually on?
docker inspect prometheus --format '{{json .NetworkSettings.Networks}}'

# Test resolution from inside the container, live
docker exec prometheus getent hosts automation-exporter
docker exec prometheus nslookup automation-exporter

Incident: the empty Grafana datasource that turned out to be a private GitHub 404

Case Study — Production Incident Timeline
T+0
A team adds a Grafana datasource pointing at http://prometheus:9090. Nobody had actually started a prometheus container on that Docker network yet — the datasource was configured against a name that, at that moment, resolves to nothing.
T+2m
To fix it fast, someone tries to grab the team's known-good prometheus.yml straight from the private GitHub repo, without cloning or authenticating:
curl -o prometheus.yml \
  https://raw.githubusercontent.com/org/private-infra-repo/main/prometheus.yml
T+2m
GitHub's raw-content service, hit without credentials against a private repo, returns HTTP 404 Not Found — deliberately, not 401 or 403. GitHub does this on purpose: returning a distinct "unauthorized" status for private repos would let an unauthenticated caller confirm the repo exists, which is itself information leakage. A private repo and a nonexistent repo must look identical to someone with no access — both return the same 14-byte body:
404: Not Found
T+2m
curl, run without -f/--fail, treats this as a success. It got an HTTP response and wrote the body to disk — curl only promotes 4xx/5xx responses to a curl-level error when you explicitly ask it to. So prometheus.yml on disk now contains the literal 14-byte string 404: Not Found, and the shell reports exit code 0.
T+3m
The team mounts this file and starts the container:
docker run -d --name prometheus --network observability_default \
  -v "$(pwd)/prometheus.yml:/etc/prometheus/prometheus.yml:ro" \
  -v prometheus_data:/prometheus -p 9090:9090 \
  prom/prometheus:v2.52.0 --config.file=/etc/prometheus/prometheus.yml

Because docker run -d returns as soon as the container is created and started — not once the process inside is confirmed healthy — this returns a container ID immediately and everyone moves on, assuming success.

T+10m
Grafana's datasource test still fails, or worse, the Prometheus container is quietly crash-looping in the background. First diagnostic step — check actual container state, not just "did the command exit 0":
docker ps -a
CONTAINER ID   IMAGE                      STATUS
a1b2c3d4e5f6   prom/prometheus:v2.52.0    Restarting (1) 4 seconds ago

Restarting (1) 4 seconds ago is the tell: the (1) is the process's last exit code, and the fact that "N seconds ago" keeps resetting to a tiny number means the restart policy is relaunching it over and over — a crash loop, not a slow startup.

T+11m
Second diagnostic step — read what the process itself said before it died:
docker logs prometheus
ts=2026-07-10T09:14:02.113Z caller=main.go:589 level=error msg="Error loading config (--config.file=/etc/prometheus/prometheus.yml)"
err="parsing YAML file /etc/prometheus/prometheus.yml: yaml: unmarshal errors:
  line 1: cannot unmarshal !!str `404: No...` into config.plain"

Prometheus's own YAML parser is telling you, plainly, that line 1 of the config is not a map — it's trying to unmarshal the literal string 404: Not Found as if it were the whole config document, and failing.

T+12m
Confirm the root cause directly by looking at what actually got saved:
head -c 100 prometheus.yml
# 404: Not Found
T+15m
Proper fix — authenticate the request instead of silently accepting an error page as data. Three equally valid options:
# Option A: authenticated clone
git clone https://$GITHUB_TOKEN@github.com/org/private-infra-repo.git

# Option B: curl with a token AND --fail, so a future auth error is loud, not silent
curl -f -H "Authorization: Bearer $GITHUB_TOKEN" \
  https://raw.githubusercontent.com/org/private-infra-repo/main/prometheus.yml \
  -o prometheus.yml

# Option C: the authenticated GitHub CLI, which is already logged in
gh api repos/org/private-infra-repo/contents/prometheus.yml --jq '.content' \
  | base64 -d > prometheus.yml

Option B's added -f flag is the actual lesson here: it turns "curl silently saves whatever HTTP gave you" into "curl exits non-zero and prints nothing to the file on any 4xx/5xx," which is what should have caught this the first time.

T+17m
Remount the real config and restart, then re-check container state instead of trusting the command's exit code:
docker restart prometheus
docker ps -a
# STATUS: Up 8 seconds

docker logs -f prometheus
# ...level=info msg="Server is ready to receive web requests."
T+18m
Verify via Prometheus's own health endpoints — don't just eyeball the log:
curl http://localhost:9090/-/healthy
# Prometheus Server is Healthy.
curl http://localhost:9090/-/ready
# Prometheus Server is Ready.
T+19m
Verify the Grafana datasource: Connections → Data sources → Prometheus → Save & test. It only goes green now because that button itself runs a live query (typically up) against the configured URL — a moment ago that URL had nothing listening behind it at all.
T+20m
Final live verification — an actual PromQL query returning real target data, not just a green checkmark:
curl -s 'http://localhost:9090/api/v1/query?query=up' | jq
# up{job="prometheus", instance="localhost:9090"} => 1
# up{job="automation-results-exporter", instance="automation-exporter:9091"} => 1
The lesson, stated plainly

Two separate silent successes stacked on top of each other: curl exiting 0 on an HTTP-level 404 (fixed by -f), and docker run -d exiting 0 the instant the container is created, regardless of whether the process inside stays up (fixed by never trusting a launch command's exit code — always follow with docker ps -a). Neither tool lied to you; both simply answered a narrower question than the one you were actually asking.

Production deployment considerations

  • Persistent volume for TSDB data — always a named volume (prometheus_data), never a bind mount to an arbitrary host path, both for lifecycle management and to sidestep permission mismatches against the image's non-root UID.
  • Retention sizing — set both --storage.tsdb.retention.time and, if disk is a hard constraint, --storage.tsdb.retention.size (e.g. 20GB). Whichever limit is hit first wins; a busy environment with high-cardinality metrics can fill a disk well before a time-based retention window expires.
  • Resource limits — Prometheus's memory footprint is driven almost entirely by cardinality (the number of distinct active time series), not by data volume over time — the mutable head block lives fully in memory. Undersizing memory causes an OOM-kill, which is a far worse failure than a slow query; size generously and monitor prometheus_tsdb_head_series yourself.
  • Exposing port 9090 — Prometheus ships with no built-in authentication or TLS. Publishing 9090 to the open internet exposes your full metrics history and topology, and lets anyone run arbitrarily expensive queries against it (a cheap DoS vector). Keep it on a private network, behind a reverse proxy with auth, or reachable only via VPN/SSH tunnel.
  • --web.enable-lifecycle — enables hot config reload via POST /-/reload, but that endpoint is itself unauthenticated by default. Pair it with network-level restriction, not public exposure.

Introducing Prometheus Into a CI/CD-Only Pipeline

The realistic starting point: zero metrics, only pass/fail in the CI tool. Bridging that gap with a custom exporter — walked through against this repo's real, working implementation.

The realistic starting point, and why CI-native pass/fail isn't enough

Most test automation starts exactly where this repo's shell scripts describe: Jenkins or GitHub Actions runs a suite, and the only artifact of that run is a green or red status inside the CI tool itself. That gets you, at most, "did the last run pass." It does not get you:

  • Historical trend — "has pass rate degraded over the last two weeks" requires manually paging through build history in the CI UI; there is no query language for it.
  • Cross-run comparison at a glance — comparing run N to run N-10 means opening ten separate build pages.
  • Alerting on patterns, not single events — "3 consecutive failures" or "no successful run in 25 hours" are patterns across multiple runs, and CI tools generally only notify per-build, not per-pattern.
  • A shared, queryable surface other tools (Grafana, an on-call dashboard, an SLO report) can sit on top of.

What an exporter actually is, architecturally

An exporter is nothing more than a small, standalone HTTP server whose only job is to expose a /metrics endpoint in the Prometheus text format. It is a translation layer: on one side, "however your data actually lives" (a JSON blob in S3, a row in a database, a third-party API); on the other side, "what Prometheus knows how to scrape." It does not need a database of its own — an in-memory registry, refreshed on an interval, is enough.

Why ECS (and GitHub Actions runners) can't just be scraped directly

This repo's own production system is the textbook case for why the exporter pattern exists at all. ECS tasks are short-lived: they start, run the test suite, publish results, and terminate. By the time Prometheus's next scrape interval fires, the task that just ran is already gone — there is nothing left at that IP to answer a scrape, and even if there were, ECS IP reuse could hand that same address to a completely unrelated task moments later. Prometheus cannot scrape a target that no longer exists, so the target of the scrape has to be something that does persist — a long-running exporter process, separate from the ephemeral test run, whose only job is to remember the last known state and serve it forever until the next update.

Walking through the real exporter

infra/automation-exporter/index.js is a complete, working example of exactly this pattern in ~130 lines. The shape:

infra/automation-exporter/index.js (annotated excerpt)
const { Registry, Gauge, Histogram } = require('prom-client');
const { S3Client, GetObjectCommand } = require('@aws-sdk/client-s3');

const ENVS = ['staging', 'validation'];
const reg  = new Registry();

const lastRunStatus = new Gauge({
  registers: [reg],
  name: 'automation_last_run_status',
  help: '1 = passed all gates, 0 = failed',
  labelNames: ['environment'],
});

async function refresh(env) {
  const meta = await s3json(`dashboard/data/${env}-run-metadata.json`);
  lastRunStatus.set({ environment: env }, meta.status === 'passed' ? 1 : 0);
  // ...pass rate, consecutive failures, duration histogram, etc.
}

app.get('/metrics', async (_, res) => {
  res.set('Content-Type', reg.contentType);
  res.end(await reg.metrics());
});

app.listen(9091, () => {
  const run = () => Promise.allSettled(ENVS.map(refresh));
  run();
  setInterval(run, 60_000);   // poll S3 every 60s, independent of when Prometheus scrapes
});

Three design points worth being able to explain out loud:

  • The poll interval and the scrape interval are decoupled on purpose. The exporter refreshes its in-memory gauges from S3 every 60 seconds regardless of whether anyone is scraping it right now; Prometheus separately scrapes /metrics every 60 seconds per its own config. Neither side needs to know the other's schedule — the exporter always has some last-known value ready to serve.
  • Gauges, not counters, for state. automation_last_run_status, automation_pass_rate, automation_consecutive_failures are all gauges because they represent current state that can move in either direction between refreshes — a counter would be wrong here since these values are not cumulative.
  • Every environment is refreshed unconditionally, every cycle. Promise.allSettled(ENVS.map(refresh)) updates both staging and validation series on every tick, independent of anything else in the system — including, notably, independent of any dashboard-level template variable in Grafana. A metric like automation_last_run_status{environment="staging"} exists and is fresh regardless of what a Grafana dropdown happens to be set to at query time; the exporter has no concept of "which environment is currently selected in someone's browser." That separation of concerns — the exporter owns ground truth per label, Grafana owns how a human currently wants to filter/view it — is exactly why a dashboard-level filtering bug can never make the underlying data itself go stale or wrong.

Integration path 1: Jenkins-only pipeline

Jenkinsfile (excerpt)
stage('Publish results') {
    steps {
        sh '''
          aws s3 cp results/run-metadata.json \
            s3://ci-artifacts/dashboard/data/staging-run-metadata.json
        '''
        archiveArtifacts artifacts: 'results/**', fingerprint: true
    }
}

The exporter runs as its own long-lived process/container, independent of Jenkins, polling that S3 location; Prometheus's scrape_configs gets one more static target pointed at it. Optionally, install the Jenkins Prometheus metrics plugin as well — but be precise about what it actually gives you: it exposes a /prometheus endpoint on the Jenkins controller itself, with metrics about Jenkins' own health (build queue length, executor utilization, job duration) — a completely separate metric surface from your own test-result metrics. One monitors the tool; the other monitors what the tool ran.

Integration path 2: GitHub Actions-only pipeline

GitHub Actions runners — hosted or self-hosted-ephemeral — are torn down the moment a job finishes. This is the exact same architectural problem as ECS, wearing a different name: there is no stable host for Prometheus to scrape, during or after the run. The fix is the same generalized pattern, not a GitHub-specific trick:

.github/workflows/ci.yml (excerpt)
- name: Publish results to S3
  run: |
    aws s3 cp results/run-metadata.json \
      s3://ci-artifacts/dashboard/data/staging-run-metadata.json

- name: Upload artifact (GH-native, for humans browsing the run)
  uses: actions/upload-artifact@v4
  with:
    name: test-results
    path: results/

S3 (or any blob store reachable from both the runner and the long-lived exporter host) is preferred over GitHub's own artifact storage here, because GH artifacts are only fetchable via the GitHub API with a token — fine for a human browsing a run, awkward for a persistent exporter polling on an interval outside GitHub's context entirely.

When a true pull model genuinely isn't available — no persistent host exists anywhere to run a polling exporter — the accepted alternative is the Pushgateway: a small, stateful HTTP endpoint that the ephemeral job pushes a final metric snapshot to at the end of its run (curl -X POST .../metrics/job/...), and Prometheus scrapes the Pushgateway itself as a normal, stable target. The important caveat: Pushgateway metrics persist until explicitly deleted — if a job stops running and never cleans up, Prometheus will happily keep reporting a stale "success" forever. The S3-plus-polling-exporter pattern used in this repo avoids that trap entirely, because every refresh cycle re-derives state fresh from the latest object in S3 rather than accumulating whatever was last pushed.

Know-By-Heart Reference

No looking anything up. If you can't produce this cold, you're not ready for the interview or the pager.

The docker run command

  --network observability_default \
  -p 9090:9090 \
  -v prometheus_data:/prometheus \
  -v "$(pwd)/prometheus.yml:/etc/prometheus/prometheus.yml:ro" \

  --config.file=/etc/prometheus/prometheus.yml \
  --storage.tsdb.retention.time=90d \
  --web.enable-lifecycle

The four metric types, one line each

  • Counter — only goes up (or resets to 0 on restart); always wrap in rate()/increase().
  • Gauge — current value, can move either direction.
  • Histogram — cumulative le buckets + _sum/_count; quantile computed server-side; aggregatable across instances.
  • Summary — pre-computed client-side quantiles + _sum/_count; not aggregatable across instances.

rate() / irate() / increase()

  • rate() — smoothed per-second average over the window; correct for alerting.
  • irate() — last two points only; fast-twitch dashboards, never alerting.
  • increase() — total increase over the window, in human-countable units.

The histogram_quantile pattern

histogram_quantile(0.95, sum(rate(x_bucket[5m])) by (le))

The by (le) is mandatory the moment more than one instance/pod shares a job — omitting it doesn't error, it silently returns a wrong quantile.

Health checks — container and Prometheus itself

docker ps -a                       # look for "Restarting (N)"
docker logs <container>            # look for the parse/connection error
curl http://localhost:9090/-/healthy
curl http://localhost:9090/-/ready
curl -s 'http://localhost:9090/api/v1/query?query=up' | jq

job vs. instance

job = the logical group name from job_name:. instance = the specific host:port that answered the scrape. One job, many instances.

Retention

--storage.tsdb.retention.time — default 15 days if unset. Pair with --storage.tsdb.retention.size when disk is the real constraint.

The Same Thing in Kubernetes

kube-prometheus-stack, ServiceMonitor CRDs, cluster DNS instead of Docker's DNS trick — same concepts, cluster-native mechanics.

kube-prometheus-stack

The kube-prometheus-stack Helm chart is the standard way to stand this up in Kubernetes. One helm install gives you:

  • The Prometheus Operator — a controller that watches custom resources and reconciles them into a running Prometheus configuration.
  • Prometheus itself, deployed and managed via the Operator's Prometheus CRD.
  • Alertmanager, similarly managed via an Alertmanager CRD.
  • Grafana, pre-wired with the Prometheus datasource and a set of default cluster dashboards.
  • node-exporter, deployed as a DaemonSet — one pod per node, exposing host-level OS metrics (CPU, memory, disk, network) for every node in the cluster.
  • kube-state-metrics — a separate service that watches the Kubernetes API and turns object state (deployment replica counts, pod phase, node conditions) into metrics. This is distinct from node-exporter: node-exporter reports on the host OS, kube-state-metrics reports on the Kubernetes API's view of the world.
bash
helm repo add prometheus-community https://prometheus-community.github.io/helm-charts
helm install kube-prom-stack prometheus-community/kube-prometheus-stack \
  --namespace monitoring --create-namespace

ServiceMonitor and PodMonitor

Instead of hand-editing scrape_configs in a YAML file, you declare a ServiceMonitor CRD, and the Operator watches for it, generates the corresponding scrape config internally, and reloads Prometheus automatically:

servicemonitor.yaml
apiVersion: v1
kind: Service
metadata:
  name: automation-exporter
  namespace: automation
  labels:
    app: automation-exporter
spec:
  selector:
    app: automation-exporter
  ports:
    - name: metrics
      port: 9091
      targetPort: 9091
---
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: automation-exporter
  namespace: monitoring
  labels:
    release: kube-prom-stack
spec:
  namespaceSelector:
    matchNames: ["automation"]
  selector:
    matchLabels:
      app: automation-exporter
  endpoints:
    - port: metrics
      interval: 60s

The selector.matchLabels is what replaces a hand-written static_configs.targets entry — it tells the Operator "find every Service with this label, and scrape whatever port is named metrics on it." A PodMonitor is the same idea one layer lower: it selects Pods directly by label instead of going through a Service, useful when there's no stable Service object in front of the pods you want scraped.

Cluster DNS replaces the Docker network trick

Kubernetes' built-in DNS (CoreDNS) resolves <service>.<namespace>.svc.cluster.local to a Service's ClusterIP — or, for headless services, directly to the IPs of Ready pods. This is conceptually the exact same idea as Docker's embedded DNS at 127.0.0.11 resolving container names on a user-defined network: name-based service discovery instead of hardcoded IPs. The Kubernetes version is cluster-wide by default and integrates with pod readiness — DNS/Endpoints only ever include pods that have passed their readiness probe, so a resolvable name is also an implicit "this pod claims to be ready" signal, which Docker's plain container-name DNS does not give you.

Adapting the CI exporter to Kubernetes

The same infra/automation-exporter image, unchanged, becomes a Deployment (one replica is fine — it's stateless, poll-and-serve) fronted by a Service, with a ServiceMonitor pointed at it, exactly as shown above. Nothing about the exporter's own code changes; only how it's discovered changes.

Key operational differences from bare Docker

  • Resource requests/limits are mandatory citizens, not an afterthought. The scheduler needs requests to place pods sensibly across nodes; limits prevent one noisy component from starving everything else sharing a node. Prometheus especially needs a generous, deliberately-chosen memory limit given how directly cardinality drives its memory footprint.
  • PersistentVolumeClaims replace the named Docker volume — same durability goal (survive pod rescheduling), backed by whatever StorageClass the cluster provides, with the same retention/size planning concerns as before.
  • Config reload is no longer "edit the bind-mounted file and hit /-/reload." Config lives in a ConfigMap (or is generated wholesale by the Operator from your CRDs), and propagation to the running Prometheus happens either via a small reloader sidecar container that watches the mounted ConfigMap for changes and calls /-/reload itself, or — more commonly with the Operator — full reconciliation: any change to a ServiceMonitor/Prometheus CRD triggers the Operator to regenerate the entire config and push a reload automatically. You essentially never hand-edit prometheus.yml directly in this model.

Standing Up Loki From Scratch Logs

Index labels, not text — the same cost trade-off Prometheus makes for metrics, applied to logs. LogQL, Promtail, and the Explore correlation workflow.

What Loki deliberately does differently

Loki, from Grafana Labs, indexes only labels and metadata — the same small set of key-value pairs Prometheus attaches to metrics (job, namespace, pod, container) — and stores the actual log line content as compressed, unindexed chunks. This is a deliberate cost trade-off, not a limitation someone forgot to fix: a full-text index (what Elasticsearch or Splunk builds) is expensive to store and expensive to keep up to date; a label-only index is cheap, because the index stays small regardless of how much log volume flows through. The cost is that ad-hoc full-text search is slower — Loki first narrows to the matching label set cheaply, then greps the actual content of just those matched streams at query time, rather than having a pre-built inverted index over every word ever logged.

LogQL vs. PromQL, side by side

GoalPromQLLogQL
Select a stream/seriesautomation_pass_rate{environment="staging"}{job="automation-exporter", environment="staging"}
Filter contentn/a — metrics have no body to filter{job="automation-exporter"} |= "ERROR"
Rate over a windowrate(automation_tests_total[5m])rate({job="automation-exporter"} |= "ERROR" [5m])
Aggregatesum(rate(x[5m])) by (le)sum(rate({job="automation-exporter"} |= "ERROR" [5m])) by (job)

The syntax is deliberately similar on purpose: LogQL's range-vector-and-rate() mental model is copied directly from PromQL, so once you know one, the other is mostly "how do I select the right stream" rather than a whole new query language.

Promtail is the log-shipping agent — it tails files (or discovers containers) and pushes matching lines to Loki, attaching labels along the way:

promtail-config.yaml
server:
  http_listen_port: 9080

positions:
  filename: /tmp/positions.yaml

clients:
  - url: http://loki:3100/loki/api/v1/push

scrape_configs:
  - job_name: automation-exporter
    static_configs:
      - targets: [localhost]
        labels:
          job: automation-exporter
          __path__: /var/log/automation-exporter/*.log

positions.yaml tracks the last-read byte offset per file, so a Promtail restart doesn't re-ship (and duplicate) everything it already sent. __path__ is the glob Promtail tails; every line it reads gets the static labels attached (job=automation-exporter) before being pushed to Loki.

Connecting to Grafana — the metric-to-log correlation workflow

Add Loki as a datasource pointed at http://loki:3100. The payoff is the Explore split-view workflow: you notice a spike in a Prometheus panel — say, automation_failure_rate jumping at 14:32 — you switch the second Explore pane to the Loki datasource, filter by the same label ({job="automation-exporter"}), and jump to that exact timestamp. The metric told you that and when something broke; the logs at that same second tell you why.

Kubernetes variant

Loki ships as a Helm chart (grafana/loki or the simpler loki-stack), and Promtail runs as a DaemonSet — one pod per node, reading /var/log/pods/*, which the kubelet already writes every container's stdout/stderr to. The chart's default Promtail config ships with Kubernetes service-discovery relabeling rules already wired up, so pod logs are automatically labeled with namespace, pod, container, and node — the same discovery mechanism (and the same labels) that node-exporter and kube-state-metrics rely on, just applied to log shipping instead of metric scraping.

OpenTelemetry Traces + Metrics + Logs

A vendor-neutral instrumentation standard, not a Prometheus replacement — and the one tool that answers "where exactly did the time go on this one request."

What OpenTelemetry actually is

OpenTelemetry (OTel) is a CNCF specification, plus SDKs and a Collector, for producing and moving traces, metrics, and logs in a vendor-neutral format. It is not a storage backend and not a replacement for Prometheus — it's the instrumentation and pipeline layer in front of whichever backend actually stores and queries the data (Tempo for traces, Prometheus/Mimir for metrics, Loki for logs).

The OTel Collector: receivers, processors, exporters

The Collector is a configurable pipeline with three kinds of components:

  • Receivers — ingest data. The otlp receiver accepts OpenTelemetry's own wire protocol over gRPC and/or HTTP.
  • Processors — transform or filter data in flight. batch groups spans/metrics together before export for efficiency; memory_limiter protects the Collector itself from OOMing under load.
  • Exporters — send data onward. The prometheus exporter exposes an in-process /metrics endpoint for Prometheus to scrape (push-to-pull translation); the prometheusremotewrite exporter instead pushes directly to a remote-write-compatible backend; the otlp exporter forwards traces onward to a backend like Tempo.

This makes the Collector a genuine translation and aggregation layer: applications push OTLP data to it (metrics included), and it can turn around and expose that same data in a shape Prometheus's pull model expects — bridging push-instrumented applications into a pull-based metrics backend without changing how Prometheus itself works.

From-scratch deployment

otel-collector-config.yaml
receivers:
  otlp:
    protocols:
      grpc:
        endpoint: 0.0.0.0:4317
      http:
        endpoint: 0.0.0.0:4318

processors:
  batch: {}
  memory_limiter:
    check_interval: 1s
    limit_mib: 512

exporters:
  prometheus:
    endpoint: 0.0.0.0:8889
  otlp/tempo:
    endpoint: tempo:4317
    tls:
      insecure: true

service:
  pipelines:
    metrics:
      receivers: [otlp]
      processors: [memory_limiter, batch]
      exporters: [prometheus]
    traces:
      receivers: [otlp]
      processors: [memory_limiter, batch]
      exporters: [otlp/tempo]

  --network observability_default \

  --config /etc/otelcol/config.yaml

This repo already has a working, minimal instrumented client for exactly this pipeline — otel-init.js and otelTestSpan.ts, wired via NODE_OPTIONS="--require /app/otel-init.js" for auto-instrumentation, exporting OTLP HTTP to a Grafana Agent in front of Tempo. It calls span.recordException(err) and sets an error status code on test failure, and — critically — calls provider.forceFlush() after span.end(), because Playwright kills its worker processes immediately after tests finish, and without a forced flush the batch exporter's default few-second delay means the spans never leave the process at all.

Distributed tracing: what a trace and span actually are

A trace is the complete journey of one request as it crosses however many services it touches. A span is one named unit of work inside that journey — it has a start time, a duration, a parent-child relationship to other spans, arbitrary attributes, and can record an exception. Traces answer a question metrics fundamentally cannot: given this one specific slow or failed request, exactly which downstream call ate the time? A p95 latency metric tells you that 5% of requests are slow — it is an aggregate, and by construction it cannot tell you which individual request, or which specific downstream dependency, caused any one instance of that slowness. You'd need to have already suspected the cause and instrumented a metric for it. A trace shows you the actual, unpredicted culprit after the fact, because it recorded the real span-by-span breakdown of that one request as it happened.

The Tempo + Grafana pairing makes this concrete: Tempo stores traces cheaply (object-storage backed, indexing only the trace ID by default — the same "index less, store cheap" philosophy Loki applies to logs), and Grafana's trace view renders the span waterfall. This repo's own dashboards filter Tempo by a custom run.id attribute to pull up every span belonging to one specific validation run — the trace-equivalent of Loki's label filtering.

Prometheus vs. OpenTelemetry — when you need which

PrometheusOpenTelemetry
Data modelMetrics onlyTraces + metrics + logs, unified
TransportPull (scrape)Push (OTLP)
GranularityAggregated across time/instancesPer-request detail (traces)
CostCheap — fixed cardinality, fixed scrape costExpensive at full fidelity — every request is a record; sampling is usually required at scale
Best forTrends, alerting, SLOs, "is the system healthy right now"Root-causing one specific slow/failed request; vendor-neutral instrumentation portability

These are complementary, not competing: use Prometheus-style metrics to know that something is wrong and to alert on it; use OpenTelemetry traces to find out exactly where, inside one specific failing request, the time or error actually occurred. Most mature setups run both, often with the OTel Collector as the bridge that also produces Prometheus-shaped metrics from the same instrumentation.

Kubernetes variant: DaemonSet vs. Deployment gateway

  • DaemonSet — one Collector pod per node, receiving OTLP data from every pod on that node (via the node's IP or a hostPort). Adds node-level metadata cheaply, and is the natural default for always-on, infra-wide collection with minimal per-pod overhead.
  • Deployment (gateway pattern) — a centralized pool of Collector replicas behind a Service, either receiving directly from applications or receiving forwarded data from the per-node DaemonSet agents. This is the right place to centralize expensive, whole-trace-aware processing like tail-based sampling (deciding whether to keep a trace based on its final outcome — did it error, was it slow) — because that decision needs to see every span belonging to one trace in a single process, and spans of the same trace landing on different, mutually-unaware DaemonSet instances can never be correctly tail-sampled.

A common real-world topology layers both: DaemonSet agents on every node doing lightweight local batching, forwarding to a smaller centralized Deployment gateway that does the heavier trace-aware processing and final export.
