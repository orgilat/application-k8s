01What problem this solves

A Playwright HTML report answers "what happened in this run." It cannot answer:

  • Is automation health getting worse over the last two weeks?
  • Did last night's scheduled run even happen?
  • Which suite or environment currently has the worst failure ratio?
  • Should someone be paged right now?

That's the gap between test reporting and automation observability:

QuestionAnswered by
Did test X pass in this run, and why not?Playwright HTML report / CTRF JSON
Is the suite healthy right now?Prometheus gauges (automation_last_run_*)
Is it getting healthier or worse over time?History gauges + Grafana graphs
Did automation silently stop running?automation_last_run_timestamp_seconds + alert rule
Should someone be notified?Alertmanager (later — Phase 7)

This repository already generates CTRF JSON reports (Phase 1) and archives every run (Phase 2). This guide documents the exporter that bridges those JSON files into Prometheus (Phase 3 onward).

Component by component

  • Playwright — runs the suite in automation/playwright/tests/{api,ui}. Short-lived: starts, runs, writes a report, exits.
  • CTRF reporter (playwright-ctrf-json-reporter) — a Playwright reporter plugin, configured in playwright.config.ts, emitting a normalized JSON report instead of Playwright's native format.
  • latest.json — always the most recent run's CTRF report, at a fixed path, so the exporter never has to guess which file is "current."
  • runs/*.json — one archived CTRF report per run, named by run ID, never overwritten — what makes historical metrics possible.
  • automation-results-exporter — a small long-running Express service that reads both and renders them as Prometheus metrics.
  • prom-client — the Node.js Prometheus client library used to define Gauges and render the exposition format.
  • Express — the HTTP framework serving /health, /ready, /metrics.
  • /metrics — the actual scrape endpoint; recomputed on every request.
  • Prometheus — exposure-prometheus container, pulls from every target on scrape_interval: 1m.
  • Grafana, Loki, OTel/Tempo, Kubernetes/Helm — future phases, intentionally not implemented yet (§17).

04Playwright reporting setup

Configuration lives in automation/playwright/playwright.config.ts:

playwright.config.ts
const automationRunId =
  process.env.AUTOMATION_RUN_ID ||
  `run-${new Date().toISOString().replace(/[:.]/g, '-')}`;

export default defineConfig({
  testDir: './tests',
  fullyParallel: true,
  reporter: [
    ['html', { open: 'never', outputFolder: 'playwright-report' }],
    ['playwright-ctrf-json-reporter', {
      outputDir: 'results/runs',
      outputFile: `${automationRunId}.json`,
    }],
  ],
  // ...
});

Two things happen per test run:

  1. A unique run file is created. automationRunId is either passed via the AUTOMATION_RUN_ID env var, or generated from the current timestamp. The CTRF reporter writes straight to results/runs/<automationRunId>.json — Playwright itself never touches latest.json.
  2. latest.json is a separate step, handled by automation/playwright/scripts/run-with-results-history.js, run via npm run test:observed.
scripts/run-with-results-history.js
const runId = process.env.AUTOMATION_RUN_ID || `run-${new Date().toISOString().replace(/[:.]/g, '-')}`;

const child = spawn(playwrightBin, ['playwright', 'test', ...argsFromCli], {
  env: { ...process.env, AUTOMATION_RUN_ID: runId },
});

child.on('exit', (code, signal) => {
  const runResultPath = path.join(runsDir, `${runId}.json`);
  const latestPath = path.join(resultsDir, 'latest.json');

  if (fs.existsSync(runResultPath)) {
    fs.copyFileSync(runResultPath, latestPath);   // the actual "update latest" step
  }

  if (typeof code === 'number') process.exit(code);  // propagates Playwright's exit code
});

The script generates one runId, exports it as AUTOMATION_RUN_ID so Playwright's reporter uses the exact same ID, waits for the process to exit, then copies that run's file over latest.json. It always exits with Playwright's real exit code — a CI pipeline calling npm run test:observed still fails correctly when tests fail, even though latest.json gets updated either way.

Why latest.json exists

A fixed, predictable filename means the exporter's "current state" read is a single fs.existsSync + one file read — no need to sort/filter the runs/ directory to find "the most recent one" on every scrape.

Why runs/*.json exists

latest.json gets overwritten every run, so on its own it cannot answer "how many runs failed in the last week." Every run is additionally preserved, immutably, under its own run ID — supporting both current-state and historical metrics with exactly two read paths (§5).

05What the exporter is, and what this one does

A Prometheus exporter is any HTTP service that exposes GET /metrics in Prometheus's text exposition format. It is not part of Prometheus itself — it's a small adapter you write for anything Prometheus doesn't natively know how to scrape (a database, a queue, or here, a directory of JSON test reports).

This exporter, specifically:

  1. Reads results/latest.json → "what's the current state" gauges.
  2. Scans results/runs/*.json → "what's the historical state" gauges.
  3. Normalizes both into a single shape (total/passed/failed/skipped/pending/other, durationSeconds, completedAtSeconds) regardless of the underlying CTRF structure.
  4. Updates prom-client Gauge objects with those numbers.
  5. Exposes GET /health (liveness), GET /ready (resolved config), GET /metrics (the scrape target).

Nothing in the exporter runs tests, watches the filesystem, or holds state between requests — every /metrics call re-reads the files fresh. This is a deliberate simplicity trade-off: correct-by-construction (there's no cache to go stale) at the cost of a small amount of file I/O once a minute, negligible at this scale.

  // ... extracts total/passed/failed/skipped/pending/other, durationSeconds, completedAtSeconds

Responsibility: parse one CTRF JSON file into a normalized LatestRunResult — the only file that knows what a CTRF report's JSON shape looks like. Called both on latest.json (may not exist on a fresh checkout) and on every file under runs/ (could be partially written/corrupt) — missing file → emptyLatestRunResult(), and the caller additionally wraps its own call in try/catch for JSON parse errors.

src/results/runs-reader.ts

src/results/runs-reader.ts
export function readRunsHistory(resultsDir: string): RunsHistoryResult {
  const runsDir = path.join(resultsDir, 'runs');
  const history = createEmptyHistory(runsDir);
  if (!fs.existsSync(runsDir)) return history;

  const runFilePaths = fs.readdirSync(runsDir)
    .filter((f) => f.endsWith('.json'))
    .map((f) => path.join(runsDir, f));

  for (const runFilePath of runFilePaths) {
    addRunToHistory(history, runFilePath);   // via readCtrfRunResult, catches parse errors
  }
  return history;
}

Responsibility: aggregate every file under results/runs/ into totals. Re-scans the whole directory on every call — cheap at the scale of a single project's history; explicitly the place to revisit if run history grows very large (§16). A run counts as failed if it has ≥1 failed test, passed if zero failures and ≥1 test, otherwise other.

The single prom-client Registry every metric registers into — avoids a circular-import mess. collectDefaultMetrics additionally adds standard Node.js process metrics (CPU, memory, event loop lag, GC) for free.

08Gauge vs Counter

Every metric above is a Gauge, not a Counter — correct for this specific architecture, worth understanding why, not just copying.

A Prometheus Counter may only increase (reset to zero only on process restart) — it models "total events since the process started," e.g. http_requests_total in the api service. This exporter is not counting events it witnessed — it recomputes current state from files on disk, from scratch, on every scrape:

  • automation_history_runs isn't incremented once per new run — it's the count of files currently in runs/, every time /metrics is hit.
  • If old files are deleted from results/runs/ (rotation, §16), that number should legitimately go down. A Counter going down is either rejected by client libraries or misread by Prometheus as a process restart — silently corrupting any rate()/increase() query built on top.
  • The exporter has zero memory between requests — Gauge.set() is exactly "here is the current true value," full stop.

When would Counter be correct instead? An event-driven design — e.g. the exporter exposing POST /runs, incrementing an in-memory counter once per received event. That's push, not pull, and event-count, not file-scan — not what this repository implements.

Concrete warning

Do not "optimize" this exporter by switching to a Counter and incrementing it once per file found while scanning runs/. Every scrape re-scans the entire directory, so a Counter would re-count the same files again and again, growing unboundedly and lying about actual run counts. Gauge.set() (replace, not add) is the only correct operation for a "recompute from source of truth" reader.

09Docker Compose integration

docker-compose-monitoring.yml
automation-results-exporter:
  build:
    context: .
    dockerfile: apps/automation-results-exporter/Dockerfile
  container_name: exposure-automation-results-exporter
  ports:
    - "3001:3001"
  environment:
    PORT: 3001
    AUTOMATION_ENV: local
    RESULTS_DIR: /app/results
  volumes:
    - ./automation/playwright/results:/app/results:ro
  restart: unless-stopped
  networks:
    - monitoring
  • build.context: . — the repo root, not the app folder (§6, Dockerfile note).
  • ports — exposes the exporter on the host at localhost:3001 for your own browser/curl access; unrelated to how Prometheus reaches it.
  • RESULTS_DIR: /app/results — the container-side path, matching the volume mount target, not the host path.
  • volumes ... :ro — read-only. The exporter only ever reads test results; it has no business writing to them.
  • networks: [monitoring] — required so exposure-prometheus (also on monitoring) can resolve the exporter by Docker's internal DNS. Without a shared network the containers cannot reach each other by service name, regardless of published host ports.
Why automation-results-exporter:3001, not localhost:3001

Inside the exposure-prometheus container, localhost means that container itself. Docker Compose's embedded DNS resolves a service name to the right container's IP, but only for containers on the same network. This is the single most common mistake when wiring a new scrape target: copying the ports: host-side port into prometheus.yml instead of the service name.

10Prometheus YAML

monitoring/prometheus/prometheus.yml
global:
  scrape_interval: 1m
  scrape_timeout: 10s

scrape_configs:
  # ...
  - job_name: automation-results-exporter
    metrics_path: /metrics
    static_configs:
      - targets:
          - automation-results-exporter:3001
  • global.scrape_interval: 1m — applies to every job unless overridden; how often Prometheus pulls /metrics from every target.
  • job_name — becomes the job label on every metric this target produces.
  • metrics_path — explicit here, though /metrics is Prometheus's default anyway.
  • targets — Docker service name + container port, per §9.

How /targets should look once healthy — http://localhost:9090/targets:

automation-results-exporter   UP

Debugging a DOWN target, in order

  1. Is the container running? docker ps | grep automation-results-exporter
  2. Is /metrics reachable from outside Docker? curl http://localhost:3001/metrics
  3. Is it reachable from inside the Prometheus container, by service name? 
    docker exec exposure-prometheus wget -qO- http://automation-results-exporter:3001/metrics
    If step 2 works but step 3 doesn't, it's a Docker networking issue (missing networks: entry), not an application bug.
  4. Check the actual scrape error Prometheus recorded: 
    curl -s http://localhost:9090/api/v1/targets | grep -A2 automation-results-exporter
  5. Did you just edit prometheus.yml? Prometheus does not hot-reload a bind-mounted config file. docker restart exposure-prometheus (or send a reload signal if --web.enable-lifecycle is set). A newly added job simply won't appear under /targets at all until this happens.

Testing PromQL: http://localhost:9090/graph, or the HTTP API directly:

curl -s --get http://localhost:9090/api/v1/query \
  --data-urlencode 'query=automation_last_run_tests' | jq

14Jenkins integration

Not present in this repository

Same core constraint as GitHub Actions: a Jenkins pipeline stage is short-lived; the exporter must run outside the pipeline, continuously.

  1. Jenkins runs npm run test:observed inside automation/playwright.
  2. Jenkins archives automation/playwright/results/** as build artifacts, and/or uploads to shared/S3 storage.
  3. The exporter reads from a directory kept in sync with that shared location — a network volume, or a small sync job (cron + aws s3 sync, rsync) mirroring shared storage into the exporter's RESULTS_DIR.

15Adapting to existing company reporting systems

Key rule: only the reader changes. The exporter pattern stays the same.

Allure / JUnit XML / custom JSON / CI artifacts / S3
↓
a new readerparses the specific format
↓
the same normalized shapeexists, total, passed, failed, skipped, pending, other, durationSeconds, completedAtSeconds
↓
the same Prometheus metricsautomation.metrics.ts — unchanged

Concretely, to adopt this pattern against an existing Allure or JUnit XML setup:

  1. Write allure-reader.ts (or junit-reader.ts) implementing exactly the same function signature as ctrf-reader.ts's readCtrfRunResult — same return shape, same "never throw, return an empty/zeroed result with exists: false" contract.
  2. Write the equivalent of runs-reader.ts if the new format also has "many historical files," reusing the new reader per-file.
  3. Point update-latest-run.metrics.ts / update-history.metrics.ts at the new reader instead of the CTRF one.
  4. Leave automation.metrics.ts, both routers, registry.ts, config.ts, the Dockerfile, the Compose service, and the Prometheus job entirely untouched — they only ever consumed the normalized shape, never the original report format.

If a company runs multiple frameworks at once (Playwright and a Java suite emitting JUnit XML), add a suite or framework label alongside environment/status on the same metrics, with one reader per format feeding the same gauges.

16Production notes

Label cardinality

Do not put test_name, run_id, error_message, or file_path on a Prometheus label. Labels create a new time series per distinct value — unbounded cardinality (a test name, a UUID, a full error string) makes Prometheus's storage grow without bound and degrades query performance. This exporter correctly uses only environment and status — keep it that way.

  • Use logs (Loki, later) for anything you'd want to grep — which test failed and why, stack traces, full error text. Use Prometheus purely for numeric health.
  • Rotate old run files. runs-reader.ts scans the entire runs/ directory on every scrape (§6) — fine at current scale; if history grows into the thousands, add rotation or move history into a real datastore rather than scaling the per-scrape directory scan indefinitely.
  • The exporter should never run tests — it only reads files and exposes metrics.
  • CI/CD generates reports; the exporter only ever consumes them. This separation keeps it simple and stateless.
  • A Dockerfile per service is the right unit for production packaging — this exporter's own image is exactly the shape you want for an eventual Kubernetes Deployment (§17).
  • Docker Compose is for local/single-host orchestration, not a production deployment target — the natural predecessor to Kubernetes manifests once you need multi-host scheduling, autoscaling, or managed rollouts.
